# Local-only blockchain checkpoint

This prototype supports loopback HTTP RPC and chain ID 31337 only. No paid network or real funds are needed. Compile and deploy the updated contract; an older deployment is not compatible with its authorization or audit-anchor interface.

From `blockchain`, run `npm test`, `npm run node`, then in another terminal `npm run deploy:local`. Set the resulting `CONTRACT_ADDRESS` and `RPC_URL` in ignored `backend/.env`. For this synthetic environment explicitly set `LOCAL_CHAIN_DEMO=true`; this uses PUBLIC Hardhat test accounts 0 (writer), 1 (production), 2 (lab). Never fund these accounts. Otherwise configure distinct signing keys explicitly.

Contract mutations require an owner-authorized writer. Batch IDs cannot be overwritten. Release requires both distinct configured production/lab addresses; supplying a role string alone grants nothing. These addresses are controlled by one prototype backend: this demonstrates contract-level separation, not independently governed organizational approval or a professional quality certification. Legacy API operations retain their application role checks.

`AUDIT_ANCHOR_ENABLED=true` (enabled in the local demo configuration) polls persisted batch-linked `TemperatureLog` readings and append-only `ColdChainAudit` events every five seconds. For each reading, the local contract stores an append-only raw record: batch, device, vehicle, shipment, millisecond timestamp, temperature, optional humidity/battery and GPS. Decimal values are integer-scaled (0.001 for temperature/humidity/battery; 0.000001 degrees for GPS). The contract recomputes a SHA-256 commitment over the exact stored sensor fields before accepting the record. A separate event ID plus canonical JSON SHA-256 digest is also anchored for each reading; mutable evaluator status/results are excluded. Audit reasons and snapshots remain in MongoDB and only their digest is anchored. `TelemetryAnchor` and `AuditAnchor` keep durable queue state and receipts; digest anchoring and raw-record writes retry independently. Identical record retries are idempotent, while conflicting fields or digests for the same record ID are rejected. A chain outage never blocks telemetry evaluation or releases a hold.

Batch status is exposed as the latest entry in an append-only status history; the contract does not overwrite earlier statuses. Batch certificates and production/lab release sign-offs are one-time additions, and release flags only move from false to true. Other lifecycle/distribution events are appended. These are application-contract guarantees on this local chain, not a public independently governed ledger; the owner can still change writer permissions.

`GET /api/batches/:batchId/audit-anchors` requires existing batch read permission and returns digest verification plus the corresponding raw on-chain record where available. `GET /api/batches/:batchId/on-chain-telemetry?offset=0&limit=100` reads contract state directly; limit is 1–500 and pages are ordered oldest first. The Blockchain Audit panel exposes those records. System Readiness separately counts reading digests and raw on-chain sensor records. A saved `confirmed` flag is not proof if the chain was reset or evidence changed. Local Hardhat state is ephemeral; resetting the node invalidates prior evidence until the records are deliberately re-anchored. Old transaction strings and records are retained, not relabeled verified. The legacy lifecycle transaction association is explicitly labeled an inferred label match, not cryptographic proof.

Manufacturer QR payloads include the local chain ID, contract address, batch ID, latest sensor record ID and its SHA-256 commitment once a reading is anchored. `GET /api/batches/verify/:batchId` checks QR proof fields against the configured contract; a plain batch ID verifies batch identity only. The signed-in Healthcare dashboard still uses its authenticated API and organization-scoped access. The QR includes enough public identifiers and raw-record digest for an independent local-chain reader to check the record; the current browser flow itself uses the backend. The QR is not a public-chain or anonymous verification service.

There are no fabricated receipts or success-on-RPC-failure fallbacks. Non-anchor operational writes are not yet a transactional outbox; a crash after a successful chain write but before a database save can still require reconciliation. One backend process owns the queues. Direct database administrators can alter MongoDB; only an independently preserved on-chain digest can reveal such a change. A local developer chain is not an independent immutable public ledger.

Verification: six real in-process Hardhat tests cover constructor/signers, unauthorized mutations, duplicate registration, two-address release, writer revocation, immutable digest anchors, full raw telemetry storage/retry, status history and one-time certificates/sign-offs. Focused backend tests cover digest and raw-record outbox retries, integrity conflicts, proof-bearing QR verification, paginated direct chain reads and role-scoped access.
