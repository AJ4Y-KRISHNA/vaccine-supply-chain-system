## Implemented components and data flow

### Web application and API

The React entry point routes to Login, Admin, Manufacturer, Distributor, Hospital and Architecture Status pages; the role dashboards are guarded by the frontend route component. The frontend package declares React, React Router, Chart.js, Bootstrap, Tailwind and map-related dependencies: `frontend/src/App.js:1-65`, `frontend/src/components/ProtectedRoute.js:1-24`, `frontend/package.json:1-29`.

The Express server exposes authentication, distribution, forecast, sentiment, decision, batch, shipment, vaccination, dashboard, temperature, simulator, alert, traceability, manufacturer, admin, order and feedback route groups. It connects to MongoDB before listening and defaults to a loopback listener: `backend/server.js:42-84`. The frontend API client defaults to the local backend URL unless `REACT_APP_API_BASE` is configured: `frontend/src/services/api.js:1-12`.

### Persistence and inputs

Operational records are represented by Mongoose models, including batches, orders, shipments, vaccinations, temperature logs, simulator devices, cold-chain policies, alerts, and audit records: `backend/models/Batch.js:1-53`, `backend/models/Order.js:1-66`, `backend/models/Shipment.js:1-42`, `backend/models/Vaccination.js:1-35`, `backend/models/TemperatureLog.js:1-30`, `backend/models/SimulatorDevice.js:1-16`, `backend/models/ColdChainPolicy.js:1-25`, `backend/models/TemperatureAlert.js:1-76`, `backend/models/ColdChainAudit.js:1-13`.

The normal development forecast fallback is a fixed deterministic series explicitly labeled synthetic. Caller-provided forecast arrays are marked unverified; configured CSV provenance is marked operator-supplied and not independently verified: `ai-services/ingestion/demand_dataset.py:9-36`, `ai-services/forecasting/baselines.py:30-45`. The application banner labels its records and placeholder inventory as software demo/test data: `frontend/src/App.js:13-17`. These source facts do not prove the contents or provenance of the MongoDB database or any configured CSV file.

The optional local CSV seeder deserves special care: when configured, it deletes existing Shipment, Batch or TemperatureLog records in its target collection before importing rows. It is exposed as a manual `seed:real` script, not run by server startup: `backend/package.json:5-10`, `backend/scripts/seedRealData.js:33-94`, `backend/server.js:76-85`.

### AI and decision endpoints

FastAPI registers forecast, decision, sentiment and advisory anomaly-inference routers: `ai-services/main.py:1-25`. The active forecast compares deterministic naive, trailing-three-mean and drift baselines; for an explicitly monthly series of at least 24 contiguous periods it also compares a seasonal-naive-12 candidate. Selection is performed on expanding-window folds before an untouched chronological evaluation suffix, and the response includes provenance, metrics and a rules-based explanation: `ai-services/routes/forecast.py:1-50`, `ai-services/forecasting/baselines.py:1-163`, `ai-services/ingestion/demand_dataset.py:9-36`.

The FastAPI `/anomaly/detect` endpoint uses a rolling median/MAD statistical detector for temperature and optional humidity. It needs at least five historical values per metric, returns an explicit reason and `INSUFFICIENT_HISTORY` when the baseline is too small, and labels every result advisory-only: `ai-services/routes/anomaly.py:1-34`, `ai-services/anomaly_detection.py:1-90`. On new batch/device-linked temperature records, Express queries up to 30 earlier same-stream readings, excludes prior model-flagged outliers from later baselines, and calls the configured AI service with a bounded timeout (default URL is loopback). An unavailable model is recorded as such and does not interrupt policy evaluation: `backend/services/telemetryService.js:64-115`, `backend/services/aiService.js:1-173`, `backend/.env.example:29-31`.

The inference result, including its reason, is stored within the MongoDB temperature-log evaluation and exposed as a distinct event in the role-scoped batch-story response. When a policy alert is also present, its context may include the separate model result. The statistical inference does not create policy alerts, change severity, quarantine, or clear holds; approved cold-chain rules remain authoritative: `backend/services/temperatureAlertService.js:109-120`, `backend/controllers/traceabilityController.js:124-147,160-179`.

The active sentiment endpoint receives text in the request body. The optional BERT implementation is disabled unless explicitly opted in; absent that model, keyword hints produce a labeled heuristic result: `ai-services/routes/sentiment.py:42-60`, `ai-services/sentiment/bert_sentiment.py:4-96`. In the ordinary hospital-order path, the backend constructs this text from region, vaccine type and order notes, and stores the resulting sentiment/forecast/risk fields on a Pending order: `backend/controllers/orderController.js:37-137`.

The active decision endpoint computes a risk flag and recommended units from supplied/caller history, stock and sentiment, and labels the response advisory-only: `ai-services/routes/decision.py:12-77`. Separately, the admin-only distribution API invokes the decision endpoint, writes a local-chain distribution/lifecycle record, creates a Shipment and records a Distribution in MongoDB when that HTTP operation is called: `backend/routes/distributionRoutes.js:20-21`, `backend/controllers/distributionController.js:72-175`. The frontend Admin order-review path uses explicit batch/distributor allocation and a separate review service: `frontend/src/pages/AdminDashboard.js:297-310,797-864`, `backend/routes/orderRoutes.js:19-22`, `backend/services/orderAllocationService.js:33-100`. Thus the Python decision response is advisory, but the separate admin distribution endpoint is executable on an authorized request; the code does not implement an autonomous Oracle loop.

### Virtual telemetry and cold-chain evaluation

The software simulator uses a seeded generator and configurable simulation clock, supports NORMAL, HIGH_TEMPERATURE, LOW_TEMPERATURE, GPS_MOVEMENT and BATTERY_DRAIN scenarios, and generates temperature, humidity, location and battery fields: `backend/services/iotSimulator.js:1-13,32-109,114-212`. Device snapshots and pending readings are checkpointed in MongoDB; restored devices are initialized from saved snapshots by the durable manager: `backend/services/durableSimulator.js:10-20,39-50`, `backend/models/SimulatorDevice.js:1-16`. The simulator supports MQTT publishing and authenticated HTTP transport. In gateway mode, HTTP posts to the separately run `backend/edge-gateway/server.js` process, which validates with the shared Joi schema and forwards to the existing `/api/temperature/ingest` API; its gateway key is separate from the backend temperature key. Direct HTTP and the legacy backend MQTT subscriber remain compatibility paths: `backend/services/simulatorTelemetryTransport.js`, `backend/edge-gateway/app.js`, `backend/edge-gateway/mqttBridge.js`, `backend/services/telemetryValidation.js`, `backend/services/mqttTelemetry.js`, `backend/routes/temperatureRoutes.js`. This is virtual telemetry, not physical sensor integration. The gateway's HTTP acceptance path passed, but a live MQTT broker flow has not been verified in this phase.

Simulator and temperature-ingestion readings are persisted to the TemperatureLog collection and passed to the evaluation service: `backend/services/telemetryService.js:1-18,22-44`, `backend/models/TemperatureLog.js:1-30`. The existing temperature API requires its backend API key and retains its ingest/read routes: `backend/routes/temperatureRoutes.js:6-20`. The Edge Gateway has a distinct local API key and forwards with the backend key; for gateway-owned MQTT, set `MQTT_TELEMETRY_SUBSCRIBER_ENABLED=false` on the backend to avoid duplicate topic consumers. The gateway has no durable local spool, and Redis Streams/independent stream consumers remain unimplemented: `backend/edge-gateway/.env.example`, `backend/.env.example`, `backend/edge-gateway/server.js`.

Valid coordinates from batch-linked readings are also persisted in the MongoDB `LocationHistory` collection: `backend/services/telemetryService.js:63-73`, `backend/models/LocationHistory.js:1-21`. The authenticated `GET /api/location-history/:batchId` route is mounted in Express, applies batch-read authorization and returns points in chronological order: `backend/server.js:69`, `backend/routes/locationHistoryRoutes.js:1-8`, `backend/controllers/locationHistoryController.js:3-14`, `backend/middleware/identityScope.js:43-48`. The shared shipment visualizer first loads role-scoped shipments and then fetches location history for each visible batch. It uses points with an exact matching shipment ID; legacy points with no shipment ID are used only when the returned shipment list contains a single shipment for that batch: `frontend/src/services/liveShipments.js:1-13`, `frontend/src/components/LiveShipmentVisualizer.js:127-223`. Leaflet draws the stored points and joins them with straight lines over OpenStreetMap tiles; an exact-shipment current reading is appended only if its timestamp is at least as recent as the latest history point: `frontend/src/components/ShipmentLocationMap.js:1-100`. Admin and Distributor already use the visualizer; Manufacturer now uses it as well: `frontend/src/pages/AdminDashboard.js:579`, `frontend/src/pages/ManufacturerDashboard.js:410`, `frontend/src/pages/DistributorDashboard.js:318`. This is a map of saved simulated coordinates, not live tracking, GPS road snapping, a routed trip or proof that the truck visited the named destination; map tiles require browser network access.

Cold-chain evaluation reads a stored ColdChainPolicy for a batch. Policy fields include temperature limits, optional humidity limits, allowed duration/gap, sensor-health limits, source reference and approver: `backend/models/ColdChainPolicy.js:3-25`, `backend/services/temperatureAlertService.js:83-138,148-178`. The service records explainable alert phases; sustained excursions can quarantine batches and linked shipments, while recovery does not itself clear a quality-review hold: `backend/services/temperatureAlertService.js:21-79,83-138`, `backend/services/coldChainActions.js:5-55`. Policy review, alert review and clearance use authenticated alert routes: `backend/routes/alertRoutes.js:1-18`.

The Admin supply-planning endpoint uses a deterministic min-cost max-flow assignment: it maximizes allocated doses, then minimizes order-priority rank, eligible batch-expiry rank and operator-entered transit time subject to stock, matching product, expiry-at-arrival, order demand, shared hospital capacity and total transport capacity. Inventory eligibility already excludes ownership, release, quality-hold, disposition and data-integrity failures. Plans are saved as advisory `SupplyPlan` records and do not reserve stock or dispatch; transit inputs are not route calculations: `backend/services/supplyPlanner.js:1-167`, `backend/services/inventoryEligibility.js:10-43`, `backend/routes/adminRoutes.js:26-38`, `backend/models/SupplyPlan.js:1-5`.

### Blockchain and audit

The configured Hardhat network is localhost at chain ID 31337; the deployment script checks that chain ID before deploying: `blockchain/hardhat.config.js`, `blockchain/scripts/deploy.js`. The active backend blockchain service accepts loopback RPC only and checks chain ID 31337 before contract access: `backend/services/blockchainService.js`. The contract defines batch registration, distinct production/lab release signers, lifecycle/distribution records, one-time inventory certificates, append-only batch status history and digest anchors. It stores raw temperature, humidity, battery, GPS, device, vehicle, shipment and timestamp fields in append-only per-batch history. Sensor decimals are integer-scaled; the contract recomputes a SHA-256 field commitment before storing each record. Replays with the same record ID and matching digest do not duplicate history; conflicting evidence is rejected. Status updates append new status entries; earlier entries are retained. Release approvals are one-time, monotonic sign-offs: `blockchain/contracts/VaccineSupplyChain.sol`, `backend/services/blockchainService.js`.

When `AUDIT_ANCHOR_ENABLED=true`, the durable worker independently queues a canonical reading digest and the full raw reading for each persisted batch-linked `TemperatureLog`; cold-chain audit details remain in MongoDB and their event digests are anchored. Digest and raw-record failures retry independently. `GET /api/batches/:batchId/audit-anchors` recomputes and verifies evidence against the configured live contract. `GET /api/batches/:batchId/on-chain-telemetry?offset=0&limit=100` reads paginated sensor history directly from contract state; QR verification checks a selected chain record and digest. MongoDB remains the application query source. Local Hardhat is ephemeral and centrally operated, so these records are not a public or independently governed ledger: `backend/services/auditAnchoring.js`, `backend/models/TelemetryAnchor.js`, `backend/models/AuditAnchor.js`, `backend/routes/batchRoutes.js`, `backend/services/blockchainService.js`, `backend/services/systemReadiness.js`, `frontend/src/components/SystemReadinessPanel.js`, `frontend/src/components/BlockchainLog.js`.

### Notifications and optional email

Policy alert stages first persist the existing deduplicated in-app notifications for Admin, the owning Manufacturer, and the assigned Distributor/Healthcare recipients. When `ALERT_EMAIL_ENABLED=true`, separate outbox records are created for active Admin users and active Manufacturer users matching the batch organization; in-app notification persistence and policy actions continue if email queueing or the provider fails. The worker starts after MongoDB connects, retries provider failures with bounded backoff, and stores status/error/attempt information in MongoDB. `ALERT_EMAIL_TRANSPORT=console` only previews messages in the backend log; the SendGrid transport records a provider-accepted response (HTTP 202), not inbox delivery. Admins can inspect status through `GET /api/admin/email-deliveries`. Email is disabled by default, the provider is not exercised by the integrated acceptance script, and no SMS delivery is implemented: `backend/services/coldChainActions.js:11-64`, `backend/services/emailOutbox.js:5-123`, `backend/services/emailTransport.js:1-31`, `backend/models/EmailDelivery.js:1-24`, `backend/controllers/emailDeliveryController.js:1-20`, `backend/routes/adminRoutes.js:1-23`, `backend/server.js:84-87`, `backend/.env.example:35-41`.
